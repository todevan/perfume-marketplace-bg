# Full Project Audit — 2026-08-02

## Document purpose

This document records the repository-wide audit of the Bulgarian perfume marketplace and the verified state after the narrowly scoped Phase 1 repair batch.

The audit covered frontend and user experience, server architecture, domain logic, contracts, authentication, privacy, security, Supabase migrations and Edge Functions, storage, tests, dependencies, CI/CD, Cloudflare configuration, operational scripts, legal readiness, backups, monitoring, and project documentation.

Risk labels describe the risk of implementing a fix:

- **Low risk:** localized, reversible, and unlikely to affect authorization, persistent data, or external services.
- **Higher risk:** affects authentication, database authorization, privacy, storage, providers, legal obligations, deployment, or production data.

No credential values are reproduced in this report.

## Executive verdict

The repository is a substantial marketplace implementation rather than a visual prototype. Production-mode routes are generally connected to Supabase-backed services and database workflows. The project has a strong server-first architecture, broad test coverage, forward-only migrations, Row Level Security, private storage, moderation workflows, and careful closed-beta controls.

After Phase 1, the local application compiles, tests, and builds successfully using the declared Node.js and pnpm versions. This establishes a green development baseline.

The project is still **not production-launch-ready**. Important security, privacy, legal, provider, monitoring, backup, and real-environment gates remain unresolved. The most urgent unresolved operational issue is a credential-shaped Resend value in `.env.example`; it must be treated as exposed and rotated independently of source cleanup.

## Architecture and implemented behavior

### Server architecture

The application follows a coherent server-first design:

1. `src/hooks.server.ts` creates the request-scoped Supabase client, resolves closed-beta authorization, applies route policy, and controls response caching.
2. Server routes parse requests and coordinate actions.
3. Services validate Zod contracts and enforce workflows.
4. Repositories access data through the caller's Supabase client and rely on Row Level Security.
5. Stateful marketplace transitions are protected primarily by database triggers and `SECURITY DEFINER` RPCs.
6. Domain modules contain deterministic presentation and marketplace rules.

This separation is appropriate for a privacy-sensitive marketplace.

### Working product journeys

The following journeys have real production-mode implementations:

- Invite-only login and account activation.
- Password reset and authentication callbacks.
- Onboarding and consent collection.
- Bulgarian phone OTP verification.
- Staff MFA route flow.
- Public catalog, brand, fragrance, wanted, merchant, and profile discovery.
- Search, filtering, sorting, favorites, and saved searches.
- Listing draft creation and publication.
- Evidence-image upload through a protected endpoint.
- Structured offers and swaps.
- Conversations unlocked by accepted offers.
- Double-confirmation deal completion, cancellation, and disputes.
- Reviews tied to completed deals.
- Reports and moderation queues.
- Notifications and durable delivery/cleanup queues.
- Merchant applications and staff review state.
- Admin/moderator workflows and audit trails.

### Intentional restrictions

The following are deliberate closed-beta choices and were not classified as defects:

- Public signup is disabled.
- Registration is invite-only.
- Public profile writes are restricted.
- Payments, paid ranking, boosts, and advertising are disabled.
- Payment and delivery happen outside the platform.
- Merchant document upload is disabled during the beta.
- Chat attachments are deferred.
- Search-engine indexing is restricted for the closed beta.
- Demo mode does not persist data.
- Phone verification is required for sensitive marketplace actions.

## Phase 1 repairs completed

### 1. Local toolchain alignment

The project declares Node.js 22 and pnpm 11.9.0 in `package.json`, `.node-version`, and `.nvmrc`.

The host initially used Node 26 with a broken system pnpm/Corepack shim. A user-local Node 22.23.2 runtime and pnpm 11.9.0 launcher were established without changing `package.json` or `pnpm-lock.yaml`.

`pnpm install --frozen-lockfile` completed with the lockfile already up to date.

### 2. ListingCard compile failure

`src/lib/components/ListingCard.svelte` contained two copies of:

- `FavoriteActionData`.
- `favoriteState`, `favoritePending`, and `favoriteError`.
- `enhanceFavorite`.
- `profileKindLabel`, `bottleVolumeLabel`, and `remainingLabel`.

The second copy also initialized favorites to `false`, contradicting the intended initial state from `listing.isFavorite`.

The duplicate block was removed. The component now uses the existing shared label helpers from `card-view-model.ts` and preserves the correct favorite initialization.

Fix risk: low.

### 3. Strict demo-mode validation

`src/lib/server/env.ts` previously enabled demo mode only for `true` but silently interpreted every other value as production mode.

Runtime validation now behaves as follows:

- `PUBLIC_DEMO_MODE=true` enables demo mode only in development.
- `PUBLIC_DEMO_MODE=false` selects production-backed mode.
- An omitted value retains the existing default behavior.
- Any other populated value, such as `1`, `yes`, or `TRUE`, raises `RuntimeConfigurationError`.

Fix risk: low.

## Unresolved findings

### Critical — credential-shaped value committed in `.env.example`

Evidence: `.env.example:33-35` contains a populated `RESEND_API_KEY`-shaped value rather than an empty example.

Potential impact:

- Anyone with repository access may be able to send email through the associated provider account if the value is or was valid.
- Removing the current text does not revoke the credential or remove Git-history exposure.

Required response:

1. Revoke or rotate the provider credential.
2. Update legitimate deployments.
3. Inspect provider activity.
4. Replace the tracked example with an empty placeholder.
5. Decide separately whether coordinated Git-history remediation is necessary.

Fix risk: low source-code risk; higher operational risk. This was not changed in Phase 1 because the approved implementation scope did not include credential operations.

### High — database staff authorization does not enforce MFA

The SvelteKit admin guard requires an allowed staff role and AAL2, but database `is_staff`/`is_admin` authorization does not inspect authentication assurance level. Staff RPCs are granted to authenticated callers and rely on those database role checks.

Potential impact: an attacker holding a staff AAL1 Supabase session could bypass the `/admin` route and invoke moderation RPCs directly.

Required response: add a central database AAL2 helper and apply it to every privileged policy/RPC, then verify with hostile-client tests.

Fix risk: higher.

### High — report-evidence ownership needs hosted verification

Report evidence is uploaded through a service-role client and the report is then submitted through the normal authenticated client. Database validation checks path structure and object existence, but current static tests do not prove all hosted Storage ownership, access, finalization, and cleanup semantics.

Required response: verify the complete flow against hosted Supabase and either use authenticated storage policies or explicitly bind uploader identity in a server-only allocation/finalization workflow.

Fix risk: higher.

### Medium — message history can be rewritten or undeleted indefinitely

Senders can update message bodies, set deletion timestamps, and clear deletion timestamps while the conversation remains open. There is no edit deadline or immutable content revision demonstrated at the database boundary.

Potential impact: old content can change after a report or dispute, weakening moderation evidence.

Required response: define an edit deadline, irreversible user deletion semantics, and immutable revisions/hashes or moderation snapshots.

Fix risk: higher.

### Medium — blocking does not clearly stop incoming messages

Blocking is stored per conversation member. Message insertion validates sender membership and conversation state but does not clearly enforce a recipient block.

Potential impact: a counterpart may continue sending messages after the user selects block.

Required response: define unilateral versus conversation-wide semantics and enforce them in the database write path.

Fix risk: higher.

### Medium — merchant document workflow is incomplete

Contracts and repositories support document paths, and moderation can generate private signed URLs, but the applicant route always submits an empty document list and there is no applicant upload endpoint.

The current UI accurately says document upload is disabled. For the closed beta, a secure manual channel may remain intentional.

Required response: either document the approved manual process or implement private authenticated upload, scanning, ownership, cleanup, retention, and moderator access.

Fix risk: higher.

### Medium — report attachments are sniffed but not sanitized

JPEG, PNG, WebP, and PDF signatures are checked, but accepted bytes are stored unchanged and later exposed to staff through signed URLs.

Potential impact: malformed, polyglot, decompression-bomb, or malicious documents may reach moderators.

Required response: quarantine and scan files, re-encode images, place dimension/decompression limits, and sanitize or safely render PDFs.

Fix risk: higher.

### Medium — request-size enforcement happens after parsing

Listing and report endpoints parse multipart bodies before applying per-file limits. The notification Edge Function performs JSON parsing when `Content-Length` is absent or misleading.

Potential impact: oversized/chunked requests may consume runtime memory before application rejection.

Required response: enforce total body limits at the Worker/proxy boundary and use bounded parsing where supported.

Fix risk: higher for parser changes; low if deployment-layer limits are proven reliable.

### Medium — notification webhook accepts weak configured secrets

The notification Edge Function requires only a non-empty shared secret, while the cleanup worker requires at least 32 bytes.

Required response: enforce the same minimum-byte requirement in both functions.

Fix risk: low.

### Medium — authenticated message abuse controls are uneven

Uploads have durable rate and queue limits, but ordinary message writes do not have equivalent per-user/per-conversation limits.

Potential impact: a compromised or abusive beta account can create message and notification spam at database speed.

Required response: add durable message-rate rules, notification coalescing, and operational alerts.

Fix risk: higher.

### Medium — production providers and schedulers remain prerequisites

The source includes provider-dependent paths, but a real release requires verified configuration for:

- SMS/phone OTP.
- Resend and a verified sender.
- Cloudflare Turnstile.
- Cloudflare Images.
- Notification Database Webhook.
- Notification email Edge Function.
- Upload cleanup Edge Function and recurring scheduler.
- Catalog synchronization.
- First-admin bootstrap.
- Hosted cron and migration inventory.

Without these, rows may queue correctly while publishing, email, cleanup, verification, or administration remains unavailable.

Fix risk: higher operational risk.

### Low — TypeScript domain transitions can drift from database workflows

The exported listing transition helper describes raw status transitions more broadly than the protected database workflow RPCs allow.

Required response: label it as presentation/prevalidation logic or align it with workflow commands and contract tests.

Fix risk: low.

## Frontend and UX findings

### Working well

- Production login and OTP flows are connected to Supabase.
- The publish wizard persists validated drafts and calls real upload/publication services in production mode.
- Demo mode is visibly identified and intentionally does not persist data.
- Transaction boundaries and off-platform payment/delivery are clearly communicated.
- Catalog aliases and normalization support Bulgarian/Cyrillic and Latin discovery.
- Core routes have responsive layouts.
- The listing wizard has strong focus management, live-region feedback, progress semantics, and labelled validation.
- Private/transactional pages are generally `noindex`.

### Incomplete or misleading controls

Visible controls without implemented behavior include:

- Dashboard more-actions button: `src/routes/dashboard/+page.svelte:53`.
- Messages more-settings button: `src/routes/messages/+page.svelte:80`.
- Conversation information button: `src/routes/messages/+page.svelte:101`.
- Listing illustration thumbnail rendered as an inactive button: `src/routes/listing/[slug]/+page.svelte:141`.
- Conversation search does not perform filtering.

Required response: implement each action or render/remove it as noninteractive UI.

Fix risk: low.

### Demo registration presentation

The demo form asks for profile type, username, and age acceptance, while its server action reads only email/redirect and does not create an account. This is acceptable for a walkthrough only if success copy clearly says it is a preview.

Fix risk: low.

### Draft autosave and upload recovery

Draft persistence occurs at selected wizard transitions rather than continuously. Selected image files remain in browser memory until upload. There is no complete durable reload recovery, resumable upload, or preview lifecycle.

Potential impact: a reload or navigation can discard substantial work.

Required response: implement debounced persistence/local recovery or change autosave language; improve preview, replacement, partial-failure, and retry behavior.

Fix risk: higher.

### Accessibility gaps

Some `aria-describedby` values reference conditional error nodes that do not always exist. Dead buttons also mislead keyboard and assistive-technology users. There is no automated axe-equivalent accessibility gate.

Required response: conditionally include error IDs, remove dead controls, add automated accessibility assertions, and perform manual keyboard/screen-reader review.

Fix risk: low.

### SEO and public metadata

Closed-beta indexing restrictions are intentional. If the site later becomes public, it lacks consistent canonical URLs, Open Graph/Twitter metadata, Product/Offer/Breadcrumb structured data, and complete dynamic sitemap verification.

Fix risk: low to moderate; not a closed-beta blocker.

### Test coverage gaps

The default test suite is broad but does not fully cover:

- Complete six-step publish and production upload behavior.
- OTP, password reset, invite acceptance, and MFA in browser tests.
- Favorites persistence, saved-search management, and notification preferences.
- Full offer, conversation, deal, dispute, cancellation, and review flows under normal CI.
- Reports, merchant application, settings, profiles, legal navigation, and moderation UI.
- Accessibility scanning and SEO contracts.
- Hosted provider and scheduler operation.

The real seller-to-buyer and moderator E2E tests exist but are opt-in.

## Legal, privacy, and operational readiness

### Legal documents are unfinished

Terms, privacy, and appeals pages contain draft markers and missing operator, controller, contact, retention, and complaint details. Finalization requires Bulgarian/EU legal advice and business decisions, not merely copy editing.

Fix risk: higher.

### Data-subject workflows are not proven

No complete self-service account deletion or personal-data export journey was identified. Retention, anonymization, evidence preservation, audit logs, completed deals, reviews, and legal holds require an explicit policy and tested workflow.

Fix risk: higher.

### Production deployment is not implemented

The tracked deployment workflow is staging-only. A production path requires protected production environments, explicit approval, separate secrets, exact-SHA checks, migration preflight, backup confirmation, smoke tests, and rollback evidence.

Fix risk: higher.

### Monitoring is incomplete

Cloudflare observability and structured request IDs exist, but the repository does not prove external uptime monitoring, error tracking, alert thresholds, on-call ownership, queue alerts, provider failure alerts, or database capacity alerts.

Fix risk: higher.

### Backups are technically strong but not operationally proven

Backup/restore scripts include encryption, reconciliation, identity checks, checkpoints, non-overwrite behavior, resume support, and post-upload verification. Missing proof includes automated frequency, owner, off-site destination, retention, RPO/RTO, a database/PITR decision, and a completed restore rehearsal.

Fix risk: higher.

### CI and supply-chain improvements

The CI workflow correctly pins Node/pnpm, performs frozen installation, runs validation/tests/check/build/E2E/database contracts, and audits dependencies. Remaining improvements include:

- Pin third-party GitHub Actions to commit SHAs rather than mutable tags.
- Add Dependabot or Renovate.
- Add scheduled dependency/security audits.
- Add CodeQL or equivalent static analysis.
- Upload Playwright reports/traces on failure.
- Enable branch protection, required checks, protected environments, and reviewers where the GitHub plan supports them.
- Align `@types/node` with the Node 22 runtime to avoid accepting unavailable Node APIs.

Fix risk: mostly low; branch/environment enforcement may be higher operationally.

### Documentation drift

Historical readiness reports represent older snapshots and should not be interpreted as current proof. README migration history omits migration `011`, and builder metadata contains stale GitHub/staging/provider state.

Fix risk: low.
