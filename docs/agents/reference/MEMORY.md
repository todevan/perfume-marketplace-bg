# Engram Memory Contract

Engram supports continuity. It is not authority, a transcript store, a task tracker,
or a substitute for GitHub, Git, tests, CI, hosted readback, or repository contracts.
Retrieve narrowly, then verify live.

## Allowed classes

### Durable owner operating rules

Write only when the owner establishes or changes a durable rule, such as one issue at
a time, smallest root-cause change, no duplicate plans/reviews, Matt primary and
Superpowers tactical, exact paste-ready Linux commands, preservation of unknown work,
or no secrets in memory.

### Repository invariants

Keep these concise and point to repository authority: access prerequisites, staff MFA,
GitHub as queue, live state outranking memory, and exact fail-closed hosted mutation.
Repository files remain the canonical home.

### Active issue checkpoint

Write only at a meaningful blocked or handoff boundary. Use
[`../templates/CHECKPOINT.md`](../templates/CHECKPOINT.md) and include issue,
branch/worktree, candidate when present, last proven state, blocker class, next safe
action, forbidden actions, and supersedes relation. Update/supersede the prior topic
instead of appending near-duplicates.

### Reusable postmortem learning

At merge/closure record issue outcome; final and merge SHAs; root cause; minimum fix;
proof and cleanup result; workflow lesson; canonical postmortem path; and that earlier
active checkpoints are superseded.

## Cadence

- Once at task start: one focused retrieval for the current issue and operating rules.
- Once when a durable decision changes.
- Once at a meaningful blocked handoff.
- Once after merge/closure.

Repository and GitHub facts do not justify repeated memory queries.

## Exclusions

Never store secrets, credentials, private or synthetic emails, tokens, links,
provider response bodies, transient browser state, private manifest contents,
screenshots, redundant command logs, or the full postmortem. Sanitize paths and
external identifiers. State explicitly which older checkpoint is superseded.
