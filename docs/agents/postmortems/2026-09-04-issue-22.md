proving the complete public email/password journey. Final candidate

## Final root causes

### Application failure

The login action used a full authentication-context loader after successful password
exchange even though redirect admission required only the verified user and beta
access state. Unrelated profile/MFA reads could therefore fail a normal-user login
with a generic application 500.

The minimum repair reused the selective admission path and retained fail-closed
handling for actual admission failures. It did not add a catch-all success fallback,
retry, or failure-hiding redirect.

### Hosted-runner incompatibility

The runner treated `received_at` as the only valid Mailtrap timestamp. The live API
returned equivalent `sent_at` and `created_at` fields, so the runner missed a real
message. The repair validates every present, preflight-approved timestamp field
against the exact transaction window while preserving inbox, recipient, origin,
count, duplicate, and link assertions.

### Fixture mismatch

A helper submitted one canonical city representation while another assertion expected
a different display representation. One transaction fixture now owns the exact city
input and expected display value.

## What worked

- Unknown staging data was preserved rather than reclassified for convenience.
- Candidate, tree, deployment, and CI evidence were bound to exact SHAs.
- Private manifests recorded intended mutations and exact ownership before action.
- Stateful uncertainty stopped the run; no blind retry followed the login failure.
- Forgery, replay, non-enumeration, RLS, confirmation, onboarding, and CAPTCHA seams
  stayed fail-closed.
- Generic 500 diagnosis followed the completed provider exchange into application
  loading instead of masking the symptom.
- Exact cleanup and independent absence readback covered every transaction-created
  resource while preserving unrelated environments and capacity.
- The final proof used a fresh disposable environment and reported PASS only after the
  complete journey and cleanup passed.

## Where the workflow wasted time and credits

- Candidates were frozen and reviewed before realistic journey seams, test discovery,
  provider schemas, and acceptance-critical documentation had settled.
- Ordinary in-scope engineering repairs triggered repeated authorization and review
  cycles instead of one final-candidate review stage.
- Multiple candidate SHAs caused repeated CI and hosted deployment identity work.
- The transient advisory outage generated a code delta and extra reviews even though
  the application candidate was not defective.
- Human CAPTCHA work was split across fragile browser contexts and repeated after a
  successful token was lost.
- Historical instructions, ad hoc prompts, repository workflow prose, tactical skills,
  and memory competed for lifecycle authority.
- Checkpoint and receipt activity sometimes became a proxy for closing the launch
  blocker.

## Contributing factors

- Provider payload assumptions were encoded without a live schema/capability preflight.
- A hosted Playwright selection could have produced a misleading result if the proof
  test was absent or undiscoverable.
- Candidate provenance once included unrelated project configuration drift.
- Hosted resources were prepared before a current-status documentation correction was
  complete.
- The human browser boundary had no durable transaction-bound profile contract.
- A transient screenshot path was not credential-safe by design.
- Local test seams did not initially mirror the post-login hosted loading path closely
  enough to expose the unrelated context read.

## Security and cleanup outcome

The final proof retained hostile CAPTCHA, replay, non-enumeration, callback/token,
confirmation, onboarding, membership, and marketplace-admission assertions. The
first failed transaction and the final passing transaction both used exact,
provenance-bound cleanup with independent absence readback.

A disposable credential appeared in a transient browser screenshot during the failed
transaction. The image was not retained and cleanup invalidated the account, but the
incident established a permanent rule: credential, confirmation, recovery, and token
surfaces run with screenshot, video, and trace capture disabled or safely redacted.

No staging or production resource, paid capacity, unknown user/data, or unrelated
provider resource was changed. No credential, private synthetic email, provider
token, confirmation/recovery link, private manifest path, screenshot, or unnecessary
provider resource identifier is included here.

## How a future agent should handle the same class of issue

1. Reject any target containing unknown data and obtain an exact disposable or
   explicitly preserved transaction envelope.
2. Build a journey matrix and realistic local seams before candidate freeze.
3. Preflight provider identity, cost, schema, timestamp, inbox, CAPTCHA, CLI, and test
   discovery contracts before provisioning.
4. Finish code, tests, fixtures, configuration, and acceptance-critical documentation;
   then freeze one exact candidate.
5. Run only the final risk-appropriate reviews and exact-SHA CI.
6. Use one private manifest and one persistent visible browser context. Disable
   sensitive capture before human credential/CAPTCHA work.
7. Persist intent before mutation, read back after it, and stop on uncertain state.
8. Diagnose generic failures with safe stage markers and minimum root-cause repair.
9. Run exact cleanup and independent absence readback before reporting PASS or safe
   failure.
10. Merge, close, write one sanitized closure memory, clean only classified worktrees,
    and stop before the next issue.
